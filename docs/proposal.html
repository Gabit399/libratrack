1. Project Description

1.1 Project title

LibraTrack — University Library Management System

1.2 Project description

LibraTrack is a web-based library management system for a university library, built with Java Spring Boot. Many campus libraries still rely on paper cards and spreadsheets: students cannot check whether a book is available without visiting the library, librarians record every loan by hand, and overdue books are difficult to track. LibraTrack moves this whole process online.

Readers register with their university email, search the catalog by title, author, ISBN or genre, see how many copies of each book are currently available and reserve a copy for pickup. A personal “My loans” page shows active reservations, borrowed books, due dates and overdue items, and allows the reader to extend a loan once. Librarians work in a separate dashboard where they add, edit and remove books, manage the number of copies, issue reserved books, register returns and monitor statistics such as active and overdue loans.

The application follows the layered Spring architecture (Controller → Service → Repository) and stores its data in a PostgreSQL database through Spring Data JPA. Pages are rendered on the server with Thymeleaf, access is protected by Spring Security with two roles (READER and LIBRARIAN), and all user input is validated with Spring Validation. The project is developed individually by one student using Git and GitHub.

1.3 Main objectives

  1. Provide an online catalog with search and filtering that shows real-time book availability.
  2. Digitise the reservation → issue → return lifecycle of a book loan.
  3. Give readers a personal space to track loans, due dates and overdue books.
  4. Give librarians tools to manage the book collection and loans in one place.
  5. Apply a clean layered Spring Boot architecture with a relational database, validation, security and tests.

1.4 Target users

UserNeeds
Reader (students, teachers)Find books quickly, know whether a copy is available, reserve it online, see due dates and avoid fines.
Librarian (administrator)Maintain the catalog, process reservations, register issues and returns, see overdue loans and basic statistics.

1.5 Problem the application solves

  • No way to check book availability remotely — readers waste time visiting the library for books that are already on loan.
  • Manual paper or spreadsheet records are slow, error-prone and easy to lose.
  • Due dates are not tracked automatically, so overdue books are noticed late.
  • Librarians have no quick overview of how the collection is used.

1.7 Expected results

  • A working Spring Boot web application with at least 8 pages (see UX/UI design) connected to a PostgreSQL database.
  • Full reservation flow: login → search → book details → reserve → “My loans”.
  • Librarian dashboard with book CRUD and loan processing.
  • Role-based security, validated forms and clear error messages.
  • Unit tests for the service layer (JUnit 5, Mockito) and a Postman collection for the REST endpoints.
  • Source code in a public GitHub repository with README and setup instructions.

5. System Architecture

LibraTrack follows the layered Spring architecture: Frontend → Controller → Service → Repository → Database.

Figure 2. Layered architecture and data flow (green — request, orange — response)

Responsibilities of the layers

LayerResponsibility in LibraTrack
ControllerProcesses HTTP requests and returns views or JSON. Example: CatalogController handles GET /books and returns the catalog.html view; LoanRestController handles POST /api/loans and returns a LoanDto. Validates input with @Valid, never contains business logic.
ServiceImplements business logic: a book can be reserved only if available copies > 0; a reader can have at most 5 active loans; a loan can be extended once; loans past the due date become OVERDUE (scheduled check with @Scheduled). Methods are @Transactional.
RepositoryHandles database access via JpaRepository interfaces, e.g. findByTitleContainingIgnoreCaseOrAuthorContainingIgnoreCase(...), findByUserIdOrderByReservedAtDesc(...), countByStatus(...).
Entity / ModelRepresents application data: User, Book, Genre, Loan; DTOs and form objects transfer data between layers.
DatabasePostgreSQL stores and manages all information; schema generated by Hibernate (ddl-auto=update) during development.

Data model (entities)

EntityFieldsRelationships
Userid, fullName, email (unique), studentId, password (BCrypt), role (READER / LIBRARIAN), createdAtOne User → many Loans
Bookid, title, author, isbn (unique), description, totalCopies, availableCopies, shelfLocation, coverUrlMany Books → one Genre; one Book → many Loans
Genreid, nameOne Genre → many Books
Loanid, reservedAt, issuedAt, dueDate, returnedAt, extended (boolean), status (RESERVED, BORROWED, OVERDUE, RETURNED, CANCELLED)Many Loans → one User; many Loans → one Book

Frontend ↔ backend communication

Most pages are rendered on the server: the browser sends a request, the controller puts data into the Model and returns a Thymeleaf template. For interactive parts the page’s JavaScript calls REST endpoints with fetch() and exchanges JSON; Spring Security protects these endpoints using the same session and a CSRF token.

MethodEndpointDescriptionAccess
GET/api/books?q=&genre=&available=Search books (live search on catalog)Reader
GET/api/books/{id}Book detailsReader
POST/api/booksCreate a bookLibrarian
PUT / DELETE/api/books/{id}Update / delete a bookLibrarian
POST/api/loansReserve a book ({ "bookId": 5 })Reader
GET/api/loans/myCurrent user’s loansReader
PATCH/api/loans/{id}/extend · /cancelExtend or cancel a loanReader
PATCH/api/loans/{id}/issue · /returnIssue a reserved book / register returnLibrarian
